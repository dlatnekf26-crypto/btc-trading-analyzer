# 대시보드 성능

2026-10-04, 동일한 Python 3.12 런타임과 Streamlit AppTest에서 이전 GitHub 커밋 `6aae053`과 새 구현을 각각 별도 프로세스로 실행했습니다. 명시적 Demo 기본 설정, 최초 실행 한 번과 반복 실행 다섯 번이며 실제 거래소 네트워크나 브라우저 정적 자원 다운로드는 포함하지 않습니다. 기본 연구·차트는 1시간에서 일봉으로 변경됐습니다.

| 측정 | 이전 | 변경 후 |
|---|---:|---:|
| 최초 스크립트 실행 | 1.767초 | 1.360초 |
| 반복 실행 중앙값 | 0.604초 | 0.177초 |
| 기본 화면 Plotly 차트 | 2개 | 1개 |
| 기본 화면 데이터 표 | 8개 | 1개 |
| 차트 JSON 합계 | 117,511바이트 | 39,779바이트 |

반복 실행은 약 71%, 차트 JSON은 약 66% 감소했습니다. 이는 해당 환경의 측정 결과이며 호스팅 서버의 전체 새로고침 시간이나 실제 Binance 응답 시간을 보장하지 않습니다. 서버가 휴면 상태에서 시작하거나 거래소 호출이 느리면 첫 방문은 여전히 더 걸릴 수 있습니다.

## 줄인 작업

- Streamlit 1.65의 상태 추적 탭과 `.open`을 사용해 선택한 탭만 계산·전송합니다. 신호 기록 조회, 지표 표, Monte Carlo 차트, 저장된 백테스트 차트를 숨겨진 상태에서 만들지 않습니다.
- 각 실제 OHLCV·지표 설정에 맞춰 시간대 특징을 한 번 계산합니다. 같은 특징을 연구·차트·종합 판단이 재사용합니다. 순수 계산만 캐시하며 방문자의 계좌·설정 기록·거래 결과는 공유하지 않습니다.
- 캐시 항목 개수와 TTL을 제한합니다. 특징 32개, 연구/종합 분석 각 12개, Live 묶음 12개입니다. 가격·봉·지표 설정이 달라지면 입력 키가 달라지고 새 계산을 합니다. 캐시 반환값은 방문자마다 복사됩니다.
- Live 묶음은 최단 필요 봉의 확정 경계를 기준으로 60초 캐시합니다. SQLite OHLCV 키도 시간대별 확정 경계를 사용하므로 분마다 같던 주봉·월봉을 다시 수집하지 않습니다. 시간대 캐시 TTL은 기본 300초와 봉 주기 중 큰 값이며 최대 하루입니다. 새 봉 경계는 즉시 새 키를 사용하므로 TTL이 새 확정 봉을 막지 않습니다.
- 거래소의 최신 닫힌 봉이 지연되어 조회 종료 경계에 도달하지 못한 응답은 SQLite에 완전한 최신 응답으로 캐시하지 않습니다. 다음 조회에서 다시 요청할 수 있습니다. 핵심 이력 부족과 오래된 봉은 종합 판단을 보류합니다.
- 한 묶음에서 거래소 클라이언트 하나를 재사용해 시장 목록·연결 초기화 반복을 줄입니다. 호출은 순차적이며 기존 rate limit, TLS, 프록시, HTTP 451 처리를 유지합니다.
- 현재가 조회 실패도 30초만 캐시해 차트 클릭마다 느린 실패를 재시도하지 않습니다. 실패 시 마지막 확정 봉 표시를 명시하며 Demo로 대체하지 않습니다.
- 수동 새로고침은 해당 시장 캐시를 갱신합니다. 요청 순서를 세션에서 소비해 자동 업데이트가 같은 강제 새로고침을 반복하지 않도록 합니다. 일반 브라우저 새로고침은 유효한 공개 시장 캐시를 재사용합니다.
- Plotly Express와 연구 실행 모듈은 해당 연구 기능을 사용할 때 가져옵니다. 고정 Demo 데이터는 제한된 항목 수로 한 시간 재사용합니다.

## 확인 범위

회귀 검사는 분 단위 새로고침 재사용, 시간·주·월의 새 경계 무효화, 윤년·월요일 경계, 수동 강제 갱신, 지연된 최신 봉 재시도, 묶음당 클라이언트 한 개, 특징·설정 변경 시 재계산, 반환값 분리를 검사합니다. UI 검사에서는 차트 조작으로 수집·지표 계산을 반복하지 않는지, 숨긴 탭의 차트가 실행되지 않는지, 현재가 실패를 짧게 재사용하는지 확인합니다.

실제 Chromium에서는 데스크톱·모바일에서 탭 클릭, 모의거래 활성화/중지, 설정 저장, 백테스트 실행 후 선택 탭 유지, 월봉 전환과 페이지 새로고침을 검사했습니다. 이는 Demo 기능 확인이며 실제 Binance 연결과 공개 배포 사이트의 속도 확인은 아닙니다.

## 미래 예측 추가 후 · 2026-10-05

직전 커밋 `e2e99ae`와 이번 변경을 같은 Python 3.12 / Streamlit AppTest에서 각각 별도 프로세스로 실행했습니다. 첫 실행 한 번과 반복 실행 다섯 번, Demo 기본 일봉 설정입니다. 아래 반복 시간은 전체 스크립트 실행이며 실제 호스팅·Binance 네트워크 시간을 포함하지 않습니다.

| 측정 | 기존 과거 유사성 | 미래 예측 추가 후 |
|---|---:|---:|
| 기본 시장 화면 최초 실행 | 1.369초 | 1.407초 |
| 기본 시장 화면 반복 중앙값 | 0.179초 | 0.204초 |
| 비교/예측 화면 최초 실행 | 0.175초 | 0.220초 |
| 비교/예측 화면 반복 중앙값 | 0.169초 | 0.161초 |
| 기본 비교/예측 차트 JSON | 24,558바이트 | 13,583바이트 |
| 기본 비교/예측 표 | 2개 | 0개 |

최종 구현의 측정에서는 예측과 최대 24회 과거 검증을 추가해 첫 계산은 늘었고, 캐시를 사용하는 비교/예측 반복 실행은 약 5%, 기본 차트 데이터는 약 45% 줄었습니다. 기본 시장 화면의 전체 실행은 조금 늘었으므로 전체 초기 접속이 빨라졌다고 해석하지 않습니다. 주된 개선은 차트 조작을 부분 갱신으로 바꾸어 전체 계산과 기록 작업을 생략하는 데 있습니다. 앞선 개발 중 측정의 0.129초와 최종 측정의 0.161초처럼 작은 차이는 실행 환경에 따라 변동합니다.

- 시장 차트와 예측 영역을 각각 하위 `st.fragment`로 분리했습니다. 그 안의 시간대·보기·기간·지표·펼침 조작으로 상위 수집·분석·신호 기록·모의거래가 다시 실행되지 않습니다. 상위 시장 새로고침·자동 업데이트·전역 설정은 계속 전체 판단을 갱신합니다.
- 실제 Chromium의 1440/390px 화면에서 시간대·모드·세부 검증·CSV 펼침을 조작하고 `Database.record_signal` 호출을 관찰했습니다. 이 조작들에서 상위 신호 기록 재실행은 0회였습니다. 브라우저 클릭부터 표시까지는 환경별 약 0.6초였으며 원격 사이트의 속도 보장은 아닙니다.
- 확정 자료의 창 특징을 한 번 만들고 검증 기준 시점마다 재사용합니다. 미래에 의존하는 전체 구간 정규화는 사용하지 않습니다. 최종 예측 결과의 캐시는 1시간·12개입니다.
- 세부 표와 CSV는 상태를 추적하는 expander가 열렸을 때만 생성·전송합니다. 기본 예측 화면은 4개 선/영역 trace를 사용하고 과거 사례 11개 trace는 과거 비교 보기에서만 전송합니다.
- Demo의 조밀한 원본 경로는 내부 LRU 1개로 재사용합니다. 외부에 돌려주는 봉은 별도 결과여서 반환값 수정이 다음 방문자의 데이터에 전파되지 않습니다. 확장 Demo 이력도 대시보드와 정확히 같은 경로를 사용합니다.
- 과거 자료의 SQLite 키는 거래소·페어·시간대·봉 수별로 유지합니다. 새 경계에서는 마지막 저장 봉부터 새 봉까지 받습니다. 일봉 3,000개 이력의 일반 새 봉 갱신은 전체 3페이지 대신 보통 1페이지입니다. 강제 갱신은 전체 요청을 수행합니다. 갱신된 최신 봉이 없거나 API가 실패하면 최신 이력으로 저장하지 않습니다. 과거 이력 키는 최대 7일, 일반 요청 키는 기존 하루 보존 정책을 사용합니다.
- 차트는 같은 시간대·기간에서 확대 상태를 유지합니다. 버튼·탭은 짧은 색상/그림자 전환을 사용하고 `prefers-reduced-motion`에서는 CSS 동작 효과를 끕니다. 모바일의 문서 가로 넘침도 검사했습니다.
